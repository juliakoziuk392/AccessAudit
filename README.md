# Access Review

Інструмент для перегляду прав доступу. Ви завантажуєте **два файли** — вивантаження з HR і список акаунтів із систем. Програма **сама визначає**, який файл що містить і яка колонка що означає, і показує ризики: звільнені працівники, конфлікти ролей, зайві права, неактивні акаунти тощо.

Дані не залишають ваш комп'ютер: сервер слухає лише `127.0.0.1` і нічого не зберігає.

## Що в проєкті

| Файл / папка | Призначення |
|---|---|
| `engine.py` | Рушій (раніше `lesson1.py`): розпізнає файли й колонки, застосовує правила. Працює і як бібліотека, і як CLI |
| `policy.json` | **Правила перевірки за замовчуванням**: дозволені ролі за посадою, конфлікти ролей, admin-ролі. Їх можна замінити у веб-інтерфейсі текстом або файлом |
| `server.py` | API для фронтенду (FastAPI) |
| `report.py` | Створює Excel-звіт (`.xlsx`) |
| `frontend/` | Веб-інтерфейс на React (Vite) |
| `sample_data/` | Приклади файлів (вигадані дані): малі `hr.csv`, `accounts.csv`; великі `hr_large.csv` (904 працівники) і `accounts_large.csv` (1001 акаунт); `hr_10000.csv` (10 000 працівників) і `accounts_10000.csv` (10 949 акаунтів, з колонкою `created`); `policy.txt` (приклад файлу правил). `generate_large_data.py` створює великі файли заново, а `generate_large_data.py 10000` — набір на 10 000 працівників |
| `requirements.txt` | Python-залежності |
| `start.bat` | Запуск одним кліком |

## Швидкий запуск

Двічі клікніть **`start.bat`** у папці проєкту. Скрипт сам:

1. перевірить Python-залежності й за потреби встановить їх;
2. один раз збере інтерфейс (потрібен Node.js);
3. запустить сервер і відкриє браузер на `http://localhost:8000`.

Щоб зупинити, закрийте чорне вікно або натисніть `Ctrl+C`. Якщо вікно одразу зникає або пише, що порт 8000 зайнятий, значить, програма вже запущена в іншому вікні.

Нижче те саме вручну.

## Встановлення вручну (один раз)

Потрібні Python 3.10+ і Node.js 18+. З кореня проєкту:

```powershell
.venv\Scripts\python.exe -m pip install -r requirements.txt
```

```powershell
npm --prefix frontend install
```

```powershell
npm --prefix frontend run build
```

## Запуск вручну

```powershell
.venv\Scripts\python.exe -m uvicorn server:app --host 127.0.0.1 --port 8000
```

Відкрийте в браузері `http://localhost:8000`. Зупинити: `Ctrl+C` у терміналі.

> Після змін у `frontend/src` потрібно знову виконати `npm --prefix frontend run build`.
> Для розробки фронтенду з автооновленням запустіть сервер як вище, а в другому терміналі `npm --prefix frontend run dev` і відкрийте `http://localhost:5173`.

## Як користуватись

1. Перетягніть у вікно два файли (CSV або Excel `.xlsx`) — у будь-якому порядку. Або натисніть **«Спробувати на прикладі»**.
2. У блоці **«Що ми знайшли у файлах»** перевірте, як програма зрозуміла файли:
   - який файл HR, а який акаунти (якщо переплутала — кнопка **«Поміняти місцями»**);
   - яка колонка що означає, з прикладом значення та позначкою впевненості: **✓ впевнено**, **перевірте**, **не знайдено**, **вручну**;
   - якщо колонку визначено неправильно, виберіть потрібну зі списку — звіт оновиться одразу.
3. За потреби змініть параметри: дата рев'ю, поріг неактивності (днів), корпоративний домен. Домен програма визначає сама за поштами з HR.
4. Дивіться результат: показники, графіки за типом і системою, найризикованіші акаунти, таблицю всіх знахідок із фільтрами.
   - **Excel-звіт:** кнопка **«⬇ Завантажити звіт Excel»** у правому верхньому куті сторінки. Файл `access_review_report.xlsx` має два листи: «Знахідки» (колонки: критичність, система, логін, email, ПІБ, посада, роль, проблема; кольори за критичністю, фільтри, закріплений заголовок) і «Підсумок» (показники та розбивка за типом і системою).
   - У таблиці «Усі знахідки» є кнопки **«⬇ Excel»** і **«⬇ CSV»**: вони зберігають лише те, що лишилось після ваших фільтрів.
5. Унизу в блоці **«Правила перевірки»** можна змінити правила текстом або завантажити файл із правилами (див. розділ «Правила перевірки» нижче).

## Як програма розпізнає дані

Вам не треба готувати файли у спеціальному форматі.

- **Формат файлу:** CSV з роздільником `,` `;` або табуляцією, кодування UTF-8 / Windows-1251, або Excel `.xlsx`.
- **Який файл HR, а який акаунти:** за наявними колонками (в акаунтах є система, логін, роль, дата входу; в HR є посада, статус, табельний номер).
- **Колонки:** за назвою (українською чи англійською: `email`, `Пошта`, `Employee ID`, `Табельний номер`, `Username`, `Логін`, `Last Seen`, `Остання активність` тощо) і за вмістом (схоже на пошту, на дату, на статус працівника).
- **Статуси працівників:** розуміє `active / terminated / leave`, а також `Активний`, `Звільнений`, `У відпустці` та подібні.
- **Дати:** `2026-11-17`, `17.11.2026`, `17/11/2026` та з часом.

Що має бути в даних, щоб звіт був повним:

| Файл | Обов'язково | Бажано |
|---|---|---|
| HR | пошта | статус, посада, ПІБ, табельний номер |
| Акаунти | пошта, система, логін, роль | дата останнього входу |

Якщо бажаної колонки немає, відповідні перевірки пропускаються, а програма попередить про це жовтою плашкою. Якщо не вдалося знайти обов'язкову колонку, вона покаже, якої саме, і ви виберете її вручну.

## Які перевірки виконуються

| Перевірка | Критичність |
|---|---|
| Працівник звільнений, а акаунт є | 🔴 Критично |
| Акаунт без працівника в HR (спільний/технічний) | 🔴 Критично |
| Конфлікт ролей (SoD), наприклад `operator` + `refund_approver` | 🔴 Критично |
| Постійна admin-роль (має бути лише через PAM) | 🔴 Критично |
| Роль не відповідає посаді | 🟠 Середньо |
| Акаунт неактивний довше за поріг | 🟠 Середньо |
| Пошта не з корпоративного домену або відсутня | 🟠 Середньо |
| Працівник у відпустці | 🟡 Низько |

## Правила перевірки

Політика безпеки — це не «дані у файлі», а ваше рішення, тому правила задаються окремо. Є три способи:

1. **Написати текстом у вебсторінці.** У самому низу сторінки блок **«Правила перевірки»**: у полі вже лежать поточні правила, змініть і натисніть **«Застосувати»**. Звіт оновиться одразу.
2. **Завантажити файл** кнопкою **«Завантажити з файлу»** (`.txt` або `.json`). Поточні правила можна зберегти у файл кнопкою **«Зберегти у файл»**, відредагувати й завантажити назад.
3. **Змінити `policy.json`** у корені проєкту: це правила за замовчуванням. Після змін перезапустіть сервер.

Власні правила запам'ятовуються в браузері, тож після перезавантаження сторінки вони лишаються. Кнопка **«Скинути до стандартних»** повертає правила з `policy.json`. Правила, які ви задали, **повністю замінюють** стандартні: розділ, якого немає, просто не перевіряється. Якщо в тексті є помилка, програма покаже номер рядка, не застосує правила й порахує за стандартними.

### Формат тексту

```
# Рядки з # — коментарі

[Ролі за посадою]
Developer: GitLab=developer
DevOps: GitLab=maintainer; GCP-prod=roles/editor, roles/viewer

[Конфлікти ролей]
BO: operator + refund_approver | створює й погоджує повернення

[Admin-ролі]
admin, root

[Неактивність, днів]
90
```

- **Ролі за посадою:** `Посада: Система=роль1, роль2; Інша система=роль`. Яка роль дозволена на цій посаді в цій системі. Будь-яка інша роль у цій системі вважається зайвою. Посада, якої тут немає, не перевіряється (програма скаже, які посади пропущено).
- **Конфлікти ролей:** `Система: роль1 + роль2 | пояснення`. Якщо в одного логіна є обидві ролі в цій системі, це конфлікт.
- **Admin-ролі:** ролі через кому, які мають видаватись лише тимчасово.
- **Неактивність, днів:** одне число.

Замість тексту можна подати JSON у форматі `policy.json` (ключі `role_model`, `sod_conflicts`, `admin_roles`, `inactive_days`).

## Командний рядок (без веб-сторінки)

Той самий рушій працює без браузера. Порядок файлів неважливий:

```powershell
.venv\Scripts\python.exe engine.py sample_data\hr.csv sample_data\accounts.csv --date 2026-11-17 -o report.csv
```

Без `-o` звіт виводиться в консоль. Додатково: `--inactive-days 60`, `--domain @company.com`, `--policy my_policy.txt` (файл із правилами, текстовий або JSON). Що саме програма розпізнала, виводиться в консоль.

## Типові проблеми

- **Сторінка пише, що не може зв'язатися із сервером:** запустіть сервер командою з розділу «Запуск».
- **Порожня сторінка на `localhost:8000`:** не зібрано фронтенд, виконайте `npm --prefix frontend run build`.
- **Усі акаунти позначені «Немає працівника в HR»:** пошти в акаунтах не збігаються з поштами в HR (порівнюються без урахування регістру й пробілів), або в полі Email вибрана не та колонка.
- **«Не вдалося визначити, який файл HR»:** скористайтеся кнопкою «Поміняти місцями».
